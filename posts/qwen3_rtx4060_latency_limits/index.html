Qwen3-0.6B 在 RTX 4060 Laptop 上的严格 TTFT / TPOT 下界#

一篇关于“推理延迟到底能压到多少”的推导笔记。本文给出延迟下界（等价于吞吐上界），它不是性能预测，也不承诺某个 kernel 一定能达到这个数。数据来自 Firefly 项目的实测与分析脚本（theoretical_limits.py），推导可复现：

所有带宽单位都是十进制（GB = 10^9 字节）；显存容量按 CUDA API 返回的字节数计（二进制）。

说明：文中涉及的具体实现参数（如 prefill chunk 大小、实测数据）以写作时的代码状态为准；方法本身不依赖这些具体数值。

0. 为什么做这件事#

跑推理时我们常被问“还能不能更快”。与其凭感觉优化，不如先把“物理上不可能低于多少”算清楚：哪些延迟是模型和硬件决定的，哪些是当前实现浪费的。这样优化就有了标尺——知道目标在哪，也知道什么时候该停止。

本文用 Qwen3-0.6B + RTX 4060 Laptop 这个具体组合，推导 TTFT（首 token 延迟）和 TPOT（每个输出 token 的解码间隔）的严格下界，并和 Firefly 的实测数据对比。

1. 范围与四种不同的“极限”#

除非表格另有说明，本文假设：单请求、batch size 1、BF16 权重与激活、无 prefix-cache 命中、greedy argmax、客户端与服务同机。

记：

  • P：从头处理的 prompt token 数。
  • L：某次 decode 之前已有的 token 数。attention 在追加当前 token 后看到 L + 1 个 token。
  • S_i：Firefly 第 i 个 prefill chunk 的大小（上限 4096）。
  • A_i：chunk i 之前的 token 数。
  • T：延迟；batch-1 decode 下 TPS = 1 / T。

下面四个量经常被混为一谈，必须分开：

  1. 物理绝对下界：把整颗 GPU 的已发布资源上限，套到“必不可少的信息搬运 + 有用计算”上。它允许模型 DAG 中本不可重叠的工作重叠，因此是刻意乐观的。
  2. 最优 DAG 下界：尊重 linear、attention、elementwise、LM head、sampling 之间的依赖关系，但假设 kernel 理想、缓存分配理想、利用率拉满。
  3. 当前 Firefly 算法下界：把当前实现强加的工作都算进去，例如标量 prefill attention、重复的指数运算、4096 token 分块、INT8 MMA 填充、split/reduce 临时缓冲。对未公开的缓存/访存速率，保留符号项。
  4. 实测延迟：包含利用率损失、缓存未命中、launch 与依赖气泡、host 调度、拷贝和服务开销。在假设一致的前提下，实测必须大于每个合法下界。

3.3 Elementwise 与 SFU 工作量#

每个 transformer 层每个 token，源码路径执行：

  • Q 的 RMSNorm（16 行 × 128）和 K 的 RMSNorm（8 行 × 128）。
  • RoPE 作用在 (16 + 8) * 64 = 1536 对元素上。当前源码对每个 head/对分别计算 powf、cosf、sinf，即每层每 token 有 1536 次 log/exp 型幂运算、1536 次余弦、1536 次正弦。角度只由位置和对决定，24 个 head 重复计算在数学上并非必要。
  • 两次 hidden-size 的 fused residual/RMSNorm 过渡（最后一次过渡是 residual 加，随后由最终 RMSNorm 处理）。
  • I = 3072 次 SwiGLU 指数。

当前 Firefly 下界对每个 rsqrtf、__expf、正弦、余弦各记一个 SFU 原始结果，对正底数 powf 保守记一组 LG2 + EX2。源码级精确 expf/powf 可能编译出更多指令，以 SASS 为准。最优 DAG 下界不计当前重复的 RoPE 超越函数调用——最优实现可以共享或递推生成正弦/余弦值，SFU 项里只留下不可避免的 SwiGLU 指数和 norm 的平方根倒数。

当前 kernel 的全局访存并不自动等于 DRAM 访存：小的中间量可以留在 L2，paged attention 的 K/V 读取在 GQA 重复 head 读取后也可能由 L2 满足。反过来，每个 kernel 边界都会物化全局张量。按源码统计，INT8 下 decode 每 token 有约 4.70 MB 固定的“非权重、非历史 KV”全局读写负载（含 Q 量化写入和当前 token 的 K/V append 路径）；量化 Q 和 scale 的读取在 28 层上再增加 59,136 * R_launch 字节/token。这些是负载计数，不是事务计数，也不是不可避免的 HBM 流量。

5.3 当前 Firefly 算法下界#

Firefly 按 4096 token 分块：

每个 chunk 都执行全部 28 层，重读全部 880,803,840 字节 transformer 权重；只有最后一个 chunk 读 311,164,928 字节的 LM head。这个分块在当前引擎中是精确的，它制造了一个整段算法没有的带宽下限。

量化 cache 的 prefill 第一个 chunk 刻意对当前 Q/K/V 调用连续的标量 attention；后续 chunk 调用量化 paged attention。对每个可见分数：

  • 第一个 chunk 标量 attention：128 次 FP32 QK 乘法、127 次归约加、分数乘法、128-lane 累加器/值更新、128 个线程冗余执行的 2 次指数、8 次 block barrier。
  • 后续 paged 量化 attention：同样的 QK 归约、scale/反量化算术、128 线程冗余的 2 次指数、值反量化/更新、8 次 barrier、block-table 与 scale 读取。

7. 数学推导给出的优化边界#

  1. TTFT：标量第一 chunk attention 和每线程冗余指数已从优化路径中移除。8K 下实测 TTFT 658.24 ms，最优 DAG 下界 394.44 ms。下一个目标是剩下的 263.81 ms，重点是：用原生 tiled INT8 prefill kernel 替换 INT8 反量化桥接，并把非 attention 的模型时间归因清楚。
  2. 短上下文 TPOT：优化或融合 7 个串行 GEMV、norm、RoPE、SwiGLU 与 LM head；保持权重流效率。L=0 附近 KV 量化几乎没有杠杆。
  3. 8K INT8 TPOT：6.42 ms 是绝对物理下限，8.23 ms 是当前实测。可信的下一个目标不低于 6.42 ms；在再改 kernel 之前，先用 Nsight 归因清楚 1.81 ms 的余量。
  4. 长上下文 TPOT：INT8 相对 BF16 有实际杠杆。32K 时严格下限是 BF16 19.20 ms、INT8 12.09 ms。假想的 INT4 能把下限降到 8.42 ms，但前提是有高效的打包 INT4 kernel 且精度可接受。
  5. 批处理：这些表都是 batch 1。batch 为 B 时权重字节可以在请求间摊销、GEMM 算术强度上升；聚合 TPS 下界需要单独的调度与 batch 形状推导。单请求延迟和聚合 TPS 是两个不同的目标。

8. 哪些无法仅凭静态规格精确确定#

一个唯一、精确的“硬件可达到的 TTFT/TPOT”不是模型维度和 GPU 头条规格的纯函数。以下都是运行时或实现变量，不是被省略的代数：

  • 选中的 cuBLAS kernel、小 M 占用与 epilogue 行为；
  • 有效 HBM 事务效率、bank/page 行为；
  • L1/L2 命中率、带宽与 load/store 发射压力；
  • 精确超越函数的编译器展开与依赖延迟；
  • 寄存器压力、占用、barrier 与指令调度；
  • 80 W 默认功耗墙下 SM/显存时钟能否同时维持；
  • CUDA Graph launch、H2D/D2H、host 同步、调度与 gRPC 延迟。

严格的做法不是编造这些速率。本文给出精确的工作/字节公式、已发布资源下界，以及对未发布资源的符号项；再用实测确定哪个符号项是活跃的。

9. 结论#

给一次推理“盖章”需要同时具备三样东西：模型级精确工作量、硬件已发布资源上限、以及诚实标注的实现项。本文用 Qwen3-0.6B + RTX 4060 Laptop 演示了这套方法：

  • batch-1 decode 由权重 + KV 的 HBM 读取支配，8K INT8 的绝对下限是 6.42 ms/token，当前实测 8.23 ms（效率 78%），剩余余量需要靠 Nsight 归因而不是盲目重写 kernel；
  • 短上下文的差距在固定 GEMV/launch/elementwise，不在 KV 带宽，INT4 救不了短上下文；
  • TTFT 的优化重点已经从“消除冗余指数”转为“原生 tiled INT8 prefill”；
  • 无法仅从规格推出唯一精确值，合理的工程做法是：公式 + 已发布下界 + 符号项，然后用实测补齐。
